# Consolidation Manifest Schema

**Version**: 1.0
**Last validated**: 2026-03-04
**Consumed by**: create-research-brief (generates), consolidate-research (parses)
**Purpose**: Structured metadata contract that travels from research design through execution to consolidation, enabling pattern-aware, provenance-enriched synthesis.

---

## Schema Definition

Every field includes a comment explaining what consolidation behavior it enables. Fields marked `# REQUIRED` must be present; all others are optional with stated defaults.

```yaml
# ============================================================================
# CONSOLIDATION MANIFEST SCHEMA v1.0
# ============================================================================
# Generated by: create-research-brief
# Consumed by: consolidate-research
# ============================================================================

consolidation_manifest:

  # --------------------------------------------------------------------------
  # 1. RESEARCH IDENTITY
  # Enables: manifest lookup, research chain linking, staleness detection
  # --------------------------------------------------------------------------
  research_id: string           # REQUIRED. Format: {product}-{topic-slug}-{YYYY-MM}
                                # Examples: agentient-firebase-functions-bp-2026-03
                                #           mcdonalds-order-accuracy-ai-2026-04
                                # Used by consolidate-research to link chain references
                                # and by freshness model to compute staleness.

  pattern: enum                 # REQUIRED. One of:
                                #   landscape_mapping
                                #   comparative_evaluation
                                #   implementation_pattern
                                #   best_practices
                                #   competitive_intelligence
                                #   market_research
                                #   user_research
                                #   economic_analysis
                                #   compliance_requirements
                                # Drives: output template selection, default consolidation
                                # mode, confidence tiering approach, downstream routing.

  topic: string                 # REQUIRED. Human-readable research topic.
                                # Example: "Firebase Cloud Functions v2 with Python runtime"

  objective: string             # REQUIRED. What decision or outcome this research supports.
                                # Example: "Establish best practices knowledge base for
                                # Claude Code skill generation targeting Agentient backend"

  model_mode: enum              # REQUIRED. One of: DUAL, FULL, SINGLE
                                # Drives: how many source outputs to expect,
                                # whether GPT-5.2 prompts were generated.

  created_at: datetime          # REQUIRED. ISO 8601. When the research brief was generated.
                                # Used for staleness calculation.

  # --------------------------------------------------------------------------
  # 2. MODEL CONFIGURATION
  # Enables: source identification, provenance weighting, capability-aware
  #          reconciliation, citation deduplication
  # --------------------------------------------------------------------------
  models: list                  # REQUIRED. 1-4 entries depending on model_mode.
    - model_id: enum            # REQUIRED. One of:
                                #   claude-opus-4-6
                                #   gemini-3.1-pro-deep-research
                                #   gpt-5.2-deep-research
                                #   gpt-5.2-chat
                                # Used by consolidate-research to match outputs to config.

      role: enum                # REQUIRED. One of:
                                #   primary_researcher       — deepest analysis + reasoning
                                #   structured_cataloger     — breadth + tables + citations
                                #   targeted_investigator    — site-restricted deep dives
                                #   recency_validator        — quick recent developments
                                #   deep_recency_investigator — extended recency with depth
                                # Drives: provenance weighting. primary_researcher output
                                # gets higher weight on reasoning claims; structured_cataloger
                                # gets higher weight on comprehensiveness claims.

      capabilities: list        # REQUIRED. Active capabilities for this execution. Values:
                                #   web_search, file_search, thinking_max, thinking_high,
                                #   thinking_medium, thinking_low, site_restrictions,
                                #   mcp_tools, adaptive_thinking
                                # Drives: provenance channel assignment on claims.
                                # file_search → provenance: internal_document
                                # site_restrictions → provenance: site_restricted
                                # web_search → provenance: web_search

      site_restrictions: list   # Optional. Domains the model was restricted to.
                                # Example: [github.com, firebase.google.com, stackoverflow.com]
                                # Only applicable when capabilities includes site_restrictions.
                                # Drives: provenance weight boost for authoritative sources.

      context_documents: list   # Optional. Filenames uploaded to the model.
                                # Example: [firebase-migration-guide.pdf, current-config.yaml]
                                # Only applicable when capabilities includes file_search.
                                # Drives: internal_document provenance tagging.

      output_token_estimate: integer  # Optional. Expected output tokens.
                                      # Used for context budget planning in consolidation.

      executed_at: datetime     # Optional. ISO 8601. Populated after execution.
                                # Used to detect execution order and temporal gaps.
                                # Null in the generated manifest; user fills after running.

  # --------------------------------------------------------------------------
  # 3. PATTERN-SPECIFIC METADATA
  # Enables: pattern-appropriate prompt generation, dimension-aware coverage
  #          checking, criteria-weighted reconciliation
  # --------------------------------------------------------------------------
  pattern_metadata:             # REQUIRED. Structure varies by pattern.

    # --- For best_practices ---
    technology_family: enum     # Required when pattern = best_practices. One of:
                                #   serverless, databases, frontend_frameworks,
                                #   infrastructure_as_code, api_development,
                                #   ci_cd_pipelines, ai_ml_platforms, mobile,
                                #   ai_agent_frameworks, unknown
                                # Drives: dimension weight defaults, technology-specific
                                # prompt fragments, file_search recommendations.

    dimension_weights:          # Required when pattern = best_practices.
                                # 8 dimensions, each high/medium/low.
                                # Drives: coverage matrix generation, prompt emphasis,
                                # consolidation completeness checking.
      environmental_context: enum       # high | medium | low
      idiomatic_patterns: enum          # high | medium | low
      anti_patterns: enum               # high | medium | low
      testing_validation: enum          # high | medium | low
      dependencies_versions: enum       # high | medium | low
      operational_awareness: enum       # high | medium | low
      decision_trees: enum              # high | medium | low
      escape_hatches: enum              # high | medium | low

    # --- For comparative_evaluation ---
    evaluation_criteria: list   # Required when pattern = comparative_evaluation.
      - criterion: string       # Criterion name. Example: "Developer experience"
        weight: number          # 0.0-1.0. Weights should sum to 1.0.
                                # Drives: weighted scoring in consolidated comparison
                                # matrix, sensitivity analysis on recommendation.
        description: string     # Optional. Brief description of what this measures.

    options_under_evaluation: list  # Required when pattern = comparative_evaluation.
                                   # Example: [ADK, LangGraph, CrewAI]
                                   # Drives: per-option analysis structure in output.

    # --- For landscape_mapping ---
    taxonomy_categories: list   # Required when pattern = landscape_mapping.
                                # Expected top-level categories.
                                # Example: [AI-native platforms, Low-code builders,
                                #           Developer tool suites, Consulting accelerators]
                                # Drives: coverage completeness check —
                                # consolidation verifies all categories were populated.

    scope_boundaries: string    # Optional. What's explicitly out of scope.
                                # Example: "Exclude pure project management tools
                                # and general-purpose AI assistants"

    # --- For implementation_pattern ---
    architecture_context: string  # Required when pattern = implementation_pattern.
                                  # Current architecture being implemented into.
                                  # Example: "Next.js 15 + Firebase + Cloud Run monorepo
                                  # with ADK orchestration layer"

    constraint_list: list       # Required when pattern = implementation_pattern.
                                # Hard constraints that filter patterns.
                                # Example: [Firebase-only backend, Python 3.12+,
                                #           Must support streaming responses]
                                # Drives: constraint-aware reconciliation — patterns
                                # violating constraints get flagged, not just tiered.

    # --- For competitive_intelligence ---
    competitors: list           # Required when pattern = competitive_intelligence.
                                # Named competitors to analyze.
                                # Example: [Replit Agent, Bolt.new, Lovable, v0]

    analysis_dimensions: list   # Optional. Defaults to [moat, positioning, pricing,
                                # features, strategy, team].
                                # Drives: per-competitor analysis structure.

    # --- For all patterns (fallback) ---
    key_questions: list         # Required when pattern-specific fields above don't apply
                                # (market_research, user_research, economic_analysis,
                                # compliance_requirements) OR as supplementary questions
                                # for any pattern.
                                # Example: ["What is the TAM for AI-powered product
                                # acceleration tools targeting solopreneurs?",
                                # "What pricing models show highest conversion?"]
                                # Drives: coverage matrix rows, gap detection.

  # --------------------------------------------------------------------------
  # 4. COVERAGE MATRIX
  # Enables: gap detection, overlap-zone cross-validation, coverage ratio
  #          quality metric computation
  # --------------------------------------------------------------------------
  coverage_matrix:              # REQUIRED.
    areas: list                 # REQUIRED. Coverage areas derived from pattern + topic.
      - area: string            # Area name.
                                # For best_practices: maps to 8 dimensions.
                                # For comparative_evaluation: maps to criteria × options.
                                # For landscape_mapping: maps to taxonomy categories.
                                # For others: maps to key_questions or derived areas.

        assigned_models: list   # REQUIRED. Model IDs assigned to cover this area.
                                # Example: [claude-opus-4-6, gemini-3.1-pro-deep-research]

        overlap_zone: boolean   # REQUIRED. True if multiple models cover this area
                                # intentionally for cross-validation.
                                # Drives: when true, consolidation expects agreement
                                # and flags disagreement as significant.
                                # When false, model is sole authority — no cross-validation.

    expected_overlap_summary: string  # Optional. Brief description of cross-validation
                                     # strategy. Example: "All 8 dimensions assigned to
                                     # both Claude and Gemini. Claude provides analytical
                                     # depth; Gemini provides breadth and citations."

  # --------------------------------------------------------------------------
  # 5. CONSOLIDATION CONFIGURATION
  # Enables: mode selection without re-derivation, verification prioritization,
  #          user preference preservation
  # --------------------------------------------------------------------------
  consolidation:                # REQUIRED.
    recommended_mode: enum      # REQUIRED. One of:
                                #   standard, adversarial, gap_driven,
                                #   confidence_weighted, depth_first,
                                #   breadth_first, agentic
                                # This is the skill's recommendation based on pattern
                                # and topic analysis.

    recommended_mode_rationale: string  # REQUIRED. Why this mode was chosen.
                                       # Example: "Best Practices pattern defaults to
                                       # gap_driven to ensure 8-dimension completeness.
                                       # Topic volatility is high, reinforcing need for
                                       # thorough coverage checking."

    pattern_default_mode: enum  # REQUIRED. Auto-derived from pattern:
                                #   landscape_mapping → breadth_first
                                #   comparative_evaluation → confidence_weighted
                                #   implementation_pattern → depth_first
                                #   best_practices → gap_driven
                                #   competitive_intelligence → adversarial
                                #   market_research → standard
                                #   user_research → depth_first
                                #   economic_analysis → confidence_weighted
                                #   compliance_requirements → gap_driven
                                # If recommended_mode differs from pattern_default,
                                # the rationale should explain why.

    user_override: enum | null  # Optional. If user explicitly requested a mode,
                                # capture it here. Takes precedence over recommended.
                                # Null if no override.

    verification_priorities: list  # REQUIRED. Top 3 items to verify post-consolidation.
                                   # Example:
                                   #   - "Cold start mitigation strategies (conflicting
                                   #      advice across community sources)"
                                   #   - "Firebase v2 pricing model (changed recently)"
                                   #   - "Python 3.12 compatibility with firebase-admin SDK"
                                   # Drives: self-review focus areas.

  # --------------------------------------------------------------------------
  # 6. RESEARCH CHAIN
  # Enables: sequential research validation, constraint propagation,
  #          cross-research consistency checking
  # --------------------------------------------------------------------------
  research_chain:               # REQUIRED. Use null values for standalone research.

    upstream_id: string | null  # Upstream research manifest ID. Null if first in chain.
                                # Example: "agentient-product-accel-market-2026-02"

    upstream_pattern: enum | null  # Pattern of upstream research. Must be populated
                                   # if upstream_id is set.

    inherited_constraints: list # Constraints carried forward from upstream research.
                                # Example: ["Target segment: solopreneur founders",
                                #           "Price ceiling: $49/month",
                                #           "Must differentiate on depth, not breadth"]
                                # Empty list if no upstream.
                                # Drives: constraint-aware reconciliation. Findings
                                # contradicting inherited constraints get flagged.

    downstream_expected:        # Optional. Planned next research in the chain.
      research_id: string       # Planned ID for downstream research.
      pattern: enum             # Expected pattern.
                                # Example: research_id: agentient-firebase-impl-2026-03
                                #          pattern: implementation_pattern
                                # Drives: "For Downstream" actionability section
                                # formatting — consolidation knows what format the
                                # next step needs.

  # --------------------------------------------------------------------------
  # 7. FRESHNESS MODEL
  # Enables: staleness detection, refresh scheduling, per-section volatility,
  #          temporal confidence decay
  # --------------------------------------------------------------------------
  freshness:                    # REQUIRED.
    topic_volatility: enum      # REQUIRED. One of: critical, high, medium, low, stable
                                #   critical: 1-month half-life (pricing, breaking changes)
                                #   high: 3-month half-life (AI tools, startup landscape)
                                #   medium: 6-month half-life (market sizing, competitive)
                                #   low: 12-month half-life (mature implementation patterns)
                                #   stable: 24+ month half-life (compliance frameworks)

    confidence_half_life: string  # REQUIRED. Duration string.
                                  # Example: "3_months", "6_months", "12_months"
                                  # Drives: staleness_risk quality metric.

    staleness_indicators: list  # REQUIRED. 2-5 specific signals that would invalidate
                                # findings. Example:
                                #   - "Firebase Functions v3 announcement"
                                #   - "Python runtime version change on Cloud Functions"
                                #   - "Major pricing model revision"
                                # Drives: refresh decision criteria.

    recommended_refresh: date   # REQUIRED. ISO date (YYYY-MM-DD).
                                # Computed: created_at + confidence_half_life.
                                # Example: "2026-06-04"

    per_section_volatility: list  # Optional. When different sections age at different
                                  # rates. Example for best_practices:
      - section: string           #   - section: "dependencies_versions"
        volatility: enum          #     volatility: critical
        reason: string            #     reason: "SDK versions change monthly"
                                  #   - section: "idiomatic_patterns"
                                  #     volatility: low
                                  #     reason: "Core patterns stable for 12+ months"
```

---

## Field Type Reference

| Type | Format | Example |
|------|--------|---------|
| `string` | Free text | `"Firebase Cloud Functions v2"` |
| `enum` | One of listed values | `best_practices` |
| `list` | YAML list | `[web_search, file_search]` |
| `integer` | Whole number | `64000` |
| `number` | Decimal | `0.25` |
| `datetime` | ISO 8601 | `2026-03-04T14:30:00Z` |
| `date` | ISO date | `2026-06-04` |
| `boolean` | true/false | `true` |
| `null` | Explicit null | `null` |

```yaml
        volatility: critical
        reason: "All three frameworks releasing features weekly"

        volatility: medium
        reason: "Core architectural approaches are more stable than features"
```

```yaml

      capabilities: [web_search, thinking_high]
```

## Validation Rules

Cross-field consistency checks that `consolidate-research` should run when parsing a manifest, and that `create-research-brief` should verify before emitting.

### Identity Validation

| Rule | Check | Severity |
|------|-------|----------|
| V-ID-1 | `research_id` matches format `{product}-{slug}-{YYYY-MM}` | Error |
| V-ID-2 | `pattern` is one of the 9 valid enum values | Error |
| V-ID-3 | `model_mode` is one of: DUAL, FULL, SINGLE | Error |
| V-ID-4 | `created_at` is valid ISO 8601 datetime | Error |

### Model Configuration Validation

| Rule | Check | Severity |
|------|-------|----------|
| V-MOD-1 | SINGLE mode → exactly 1 model entry | Error |
| V-MOD-2 | DUAL mode → exactly 2 model entries | Error |
| V-MOD-3 | FULL mode → 3-4 model entries | Error |
| V-MOD-4 | `model_id` is one of the 4 valid enum values | Error |
| V-MOD-5 | No duplicate `model_id` values in the models list | Error |
| V-MOD-6 | If `capabilities` includes `site_restrictions`, then `site_restrictions` list must be non-empty | Error |
| V-MOD-7 | If `capabilities` includes `file_search`, then `context_documents` list should be non-empty | Warning |
| V-MOD-8 | `site_restrictions` only present when `model_id` is `gpt-5.2-deep-research` | Warning |
| V-MOD-9 | `file_search` capability only present when `model_id` is `gemini-3.1-pro-deep-research` | Warning |
| V-MOD-10 | At least one model has `role: primary_researcher` | Warning |

### Pattern-Specific Validation

| Rule | Check | Severity |
|------|-------|----------|
| V-PAT-1 | If `pattern` = `best_practices`, then `technology_family` is required | Error |
| V-PAT-2 | If `pattern` = `best_practices`, then all 8 `dimension_weights` are populated | Error |
| V-PAT-3 | If `pattern` = `comparative_evaluation`, then `evaluation_criteria` is non-empty | Error |
| V-PAT-4 | If `pattern` = `comparative_evaluation`, then `options_under_evaluation` has ≥ 2 entries | Error |
| V-PAT-5 | If `pattern` = `comparative_evaluation`, criterion weights sum to 1.0 (±0.01 tolerance) | Warning |
| V-PAT-6 | If `pattern` = `landscape_mapping`, then `taxonomy_categories` is non-empty | Error |
| V-PAT-7 | If `pattern` = `implementation_pattern`, then `architecture_context` is populated | Error |
| V-PAT-8 | If `pattern` = `implementation_pattern`, then `constraint_list` is non-empty | Warning |
| V-PAT-9 | If `pattern` = `competitive_intelligence`, then `competitors` is non-empty | Error |
| V-PAT-10 | If `pattern` not in `[best_practices, comparative_evaluation, landscape_mapping, implementation_pattern, competitive_intelligence]`, then `key_questions` is non-empty | Error |

### Coverage Matrix Validation

| Rule | Check | Severity |
|------|-------|----------|
| V-COV-1 | Every `model_id` in `assigned_models` exists in the `models` list | Error |
| V-COV-2 | Every model in the `models` list appears in at least one coverage area | Warning |
| V-COV-3 | If `overlap_zone` = true, then `assigned_models` has ≥ 2 entries | Error |
| V-COV-4 | At least one area has `overlap_zone` = true (cross-validation exists) | Warning |
| V-COV-5 | For `best_practices` pattern: coverage areas map to 8 dimension names | Warning |
| V-COV-6 | For `landscape_mapping` pattern: coverage areas include all `taxonomy_categories` | Warning |

### Consolidation Validation

| Rule | Check | Severity |
|------|-------|----------|
| V-CON-1 | `recommended_mode` is one of 7 valid modes | Error |
| V-CON-2 | `pattern_default_mode` matches the defined pattern→mode mapping | Error |
| V-CON-3 | `verification_priorities` has 1-5 entries | Warning |
| V-CON-4 | If `recommended_mode` ≠ `pattern_default_mode`, then `recommended_mode_rationale` explains the divergence | Warning |

### Research Chain Validation

| Rule | Check | Severity |
|------|-------|----------|
| V-CHN-1 | If `upstream_id` is not null, then `upstream_pattern` must be populated | Error |
| V-CHN-2 | If `upstream_id` is not null, then `inherited_constraints` should be non-empty | Warning |
| V-CHN-3 | If `upstream_pattern` is populated, it is one of the 9 valid patterns | Error |
| V-CHN-4 | `downstream_expected.pattern` (if present) is one of the 9 valid patterns | Error |
| V-CHN-5 | Chain sequence is sensible: landscape→comparative, comparative→implementation, market→competitive, etc. | Info |

### Freshness Validation

| Rule | Check | Severity |
|------|-------|----------|
| V-FRE-1 | `topic_volatility` is one of: critical, high, medium, low, stable | Error |
| V-FRE-2 | `confidence_half_life` matches volatility tier (critical→1_month, high→3_months, etc.) | Warning |
| V-FRE-3 | `recommended_refresh` is a valid date after `created_at` | Error |
| V-FRE-4 | `staleness_indicators` has 2-5 entries | Warning |
| V-FRE-5 | `recommended_refresh` ≈ `created_at` + half-life duration (±30 days) | Info |

### Severity Levels

- **Error**: Manifest is structurally invalid. `consolidate-research` should surface the error and ask for correction before proceeding.
- **Warning**: Manifest is usable but potentially suboptimal. `consolidate-research` should note the warning and proceed, flagging in methodology notes.
- **Info**: Best practice suggestion. Log but don't surface to user.

## Integration Notes

### How `create-research-brief` Generates the Manifest

1. **Placement**: Emit the manifest as the final section of the research brief, in a fenced YAML block with a label comment:

````markdown
## Consolidation Manifest

Paste this manifest alongside your research outputs when running consolidation.

```yaml
# consolidation_manifest
consolidation_manifest:
  research_id: ...
  ...
```
````

2. **Generation timing**: Generate after all prompts are assembled, using the same analysis that produced the prompts (pattern classification, model role assignments, coverage matrix, risk assessment).

3. **Execution timestamps**: Leave `executed_at` as `null` on all models. Instruct the user: *"Update `executed_at` for each model after running the prompt. This enables the consolidation skill to detect temporal gaps between executions."*

4. **Completeness**: Every REQUIRED field must be populated. Run validation rules V-ID-* through V-FRE-* before emitting. If any Error-level rule fails, fix before output.

5. **Readability**: Use comments sparingly in the emitted manifest (unlike the schema, which is heavily commented). The manifest should be scannable by a human in under 60 seconds.

### How `consolidate-research` Parses the Manifest

1. **Detection**: Scan user input for a fenced YAML block containing the string `consolidation_manifest:`. Accept both:
   - Block with `# consolidation_manifest` label comment
   - Block starting directly with `consolidation_manifest:`

2. **Parsing priority**:
   ```
   User input contains manifest YAML block?
   ├── YES → Parse manifest, validate, use as configuration
   │         Log: "Manifest detected. Using manifest configuration."
   │         Run validation rules. Surface Errors, log Warnings.
   │
   └── NO  → Standalone mode
             ├── User provided topic + sources?
             │   └── Derive pattern from content analysis
             │       Infer model IDs from source heuristics
             │       Use pattern defaults for consolidation mode
             │       Build minimal coverage matrix from content
             │       Set freshness to medium (conservative default)
             │       Log: "No manifest found. Operating in standalone mode
             │             with inferred configuration."
             │
             └── Insufficient context
                 └── Ask user for topic and source identification
   ```

3. **Field usage mapping**: How each manifest section drives consolidation behavior:

| Manifest Section | Consolidation Behavior Enabled |
|------------------|-------------------------------|
| `research_id` | Research chain linking; used in output metadata |
| `pattern` | Output template selection; confidence tiering approach |
| `model_mode` | Expected source count; completeness validation |
| `models[].role` | Provenance weighting — which model to trust for which claim type |
| `models[].capabilities` | Provenance channel assignment (site_restricted > web_search > unsourced) |
| `models[].site_restrictions` | Provenance boost for claims from authoritative domains |
| `models[].context_documents` | Internal document provenance tagging |
| `models[].executed_at` | Temporal gap detection; execution freshness |
| `pattern_metadata.*` | Pattern-specific coverage checks and output structure |
| `coverage_matrix` | Gap detection; overlap-zone cross-validation enforcement |
| `consolidation.recommended_mode` | Mode selection (unless user overrides at consolidation time) |
| `consolidation.verification_priorities` | Self-review focus areas |
| `research_chain.inherited_constraints` | Constraint-aware reconciliation — flag contradictions |
| `research_chain.downstream_expected` | "For Downstream" section formatting |
| `freshness.*` | Staleness risk metric; per-section volatility in output |

4. **Graceful degradation**: If a manifest is present but partially invalid:
   - Use valid fields as-is
   - For invalid fields, fall back to inference from content
   - Note in methodology: *"Manifest partially invalid. Fields X, Y inferred from content."*

### Standalone vs. Manifest-Driven Behavior Differences

| Behavior | Standalone (No Manifest) | Manifest-Driven |
|----------|--------------------------|-----------------|
| Source identification | Heuristic-based | Explicit from `models` |
| Mode selection | Inferred from context signals | From `recommended_mode` |
| Coverage checking | Derived from content | Against `coverage_matrix` |
| Provenance weighting | Equal weight across sources | Role-aware + capability-aware |
| Output template | Generic tiered report | Pattern-specific template |
| Quality metrics | Coverage ratio only | Full 7-metric suite |
| Research chain | Not available | Constraint propagation + validation |
| Freshness model | Generic medium volatility | Topic-specific with per-section variance |

## Schema Evolution

This schema is versioned. Future additions should:

1. **Add optional fields only** — never break existing manifests by requiring new fields.
2. **Increment version** in the header when adding fields that change consolidation behavior.
3. **Document migration** — if a new version adds a field that consolidate-research uses, document the fallback behavior when processing an older manifest.

Candidates for v1.1:
- `cost_tracking` block (token usage + API costs per model, populated post-execution)
- `quality_targets` block (minimum acceptable scores for quality metrics)
- `parallel_execution` flag (whether models can run simultaneously or have dependencies)
